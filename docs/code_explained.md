# Подробный разбор кода варианта 23

## 1 Что строит программа

Программа хранит участников, задания и ответы в оперативной памяти.
Пользователь вызывает методы напрямую через локальную консоль либо через
TCP-клиент. В обоих случаях работают одни и те же операции Store.
Сервер отвечает за данные; клиент только передаёт аргументы и получает результат.
После остановки сервера данные исчезают: базы данных и файлового сохранения нет.

Это учебный прототип серверной части с собственным RPC. В задании не требуется
HTTP, HTML-страница, Flask или Django. Добавление таких слоёв не заменяло бы
предписанный TCP-протокол и лишь усложнило бы защиту работы.

Путь одного вызова:

```text
RpcClient.create_member(row)
  -> _call("create_member", [row])
  -> encode(args) -> XML в байтах
  -> pack_frame(code=1, body) -> 7 байт заголовка + XML
  -> TCP -> Handler.handle()
  -> receive_frame() -> decode() -> _dispatch()
  -> Store.create_member(row) -> _create() -> список в памяти
  -> ["ok", копия записи] -> XML -> заголовок ответа -> TCP
  -> клиент проверяет код и статус -> возвращает список
```

## 2 Как читать исходники

Начните со schema.py: там все поля и их позиции. Затем прочитайте Store в
model.py, особенно _create, _get, recent_results. После этого откройте
operations.py, codec.py, protocol.py, server.py и client.py в таком порядке.
REPL и демонстрация находятся в repl.py и demo.py. Последним прочитайте
независимый эталон в tests/test_mbt.py: он показывает, как доказана работа API.

В каждом модуле, классе и функции есть docstring — строка документации в
тройных кавычках. Её можно получить через help(Store.recent_results).
Это позволяет подробно объяснять код, соблюдая запрет методички на обычные
комментарии. Docstring не влияет на алгоритм функции.

## 3 Почему записи являются списками

Пример участника:

```python
[1, 1000, "127.0.0.1", "ru-RU"]
```

Здесь индексы 0, 1, 2 и 3 означают uid, datetime, ip и locale. Порядок нельзя
переставлять. Task и Response содержат по семь полей, как на ER-диаграмме.
Внешние ключи — task[3] и response[5]. Они ссылаются соответственно на
Member.uid и Task.uid. Это связи «один ко многим»: участник может иметь
несколько заданий, а одно задание — несколько ответов.

В _tables каждый uid служит ключом словаря, а значением остаётся список.
Словарь — вспомогательный индекс, не замена требуемого представления записи.
Индекс позволяет находить существующую запись по ключу в среднем за O(1).
list_members сортирует ключи, поэтому вывод повторяем: сначала меньший uid.

_create сначала проверяет форму списка и типы, затем под блокировкой проверяет
уникальность uid и внешний ключ. Только после успешных проверок выполняется
присваивание. Ошибка не должна оставлять частично созданную запись.

## 4 Для чего копировать данные

Список в Python изменяем. Если вернуть внутренний объект, пользователь может
выполнить row[2] = "другой IP" и обойти API. Поэтому _create копирует вход,
а _get и _list копируют выход. Копия неглубокая, но все поля схемы — только
int и str, которые неизменяемы. Вложенных изменяемых объектов в записях нет.

RLock защищает составную операцию «проверить наличие ключа и вставить запись».
Без блокировки два потока могли бы одновременно решить, что ключ свободен.
Тест test_concurrent_duplicate_is_atomic запускает двух клиентов: успех
получает ровно один, второй получает ошибку дубликата. Итог — одна запись.

## 5 Как проверяются входные данные

validate_row берёт ожидаемые типы из SCHEMAS, проверяет list и его длину,
а затем проходит по парам поле–значение–тип. Проверяется type(value) is int,
а не isinstance(value, int): в Python bool является подклассом int,
но True не должен случайно превратиться в идентификатор 1.

UID должен быть положительным целым числом. Отрицательная длительность
отклоняется. Наличие внешнего ключа проверяется до вставки. Для datetime,
completed и launched не придуманы ограничения, которых нет в задании.
Поля IP и locale трактуются как строки без проверки конкретного формата.

При ошибке модель поднимает ValueError. Сервер возвращает список
["error", текст], клиент превращает его в RpcError. Это тоже ValueError,
поэтому один REPL умеет показывать ошибки и локальной, и удалённой модели.

## 6 Как прочитать формулу выборки

Формула состоит из соединений, отбора по времени и проекции трёх полей.
Сначала T RIGHT JOIN R сохраняет каждый Response, даже если соответствующей
Task нет. Затем отбираются ответы с R.datetime > now - 9 минут. После этого
INNER JOIN с Member оставляет только строки со связанным участником.
Проекция оставляет M.ip, R.duration, T.tags.

В нашем хранилище внешние ключи обязательны и проверяются. Поэтому состояния
«ответ без задачи» и «задача без участника» через API недостижимы. На допустимых
данных исходная формула эквивалентна обходу всех ответов, поиску их задач
и участников. Это обоснованное упрощение, а не подмена RIGHT JOIN.

В recent_results порог времени вычисляется ровно один раз. Иначе на границе
разные ответы могли бы сравниваться с разными значениями now.
Для фиксированного now=1000 порог равен 460:

| datetime ответа | Сравнение | Входит |
|---|---|---|
| 459 | 459 > 460 ложно | нет |
| 460 | 460 > 460 ложно | нет |
| 461 | 461 > 460 истинно | да |
| 1001 | 1001 > 460 истинно | да |

Будущее проходит, потому что в задании нет верхней границы datetime <= now.
Если две разные записи дают одинаковые [ip, duration, tags], в результате
оставляется один список: реляционная проекция имеет множественную семантику.
Сортировка добавлена лишь для стабильности вывода и не меняет состав результата.

Алгоритм просматривает R ответов; связи ищутся через словари. Удаление дублей
через `row not in result` в худшем случае даёт O(R²). Для небольшого учебного
хранилища это простое и прозрачное решение. Результат всё равно состоит
из списков. Для больших наборов можно добавить отдельный hash-set проекций.

## 7 Как устроен XML

Кодек поддерживает три типа: int, str и list. Тип явно задаётся именем тега.
Пример аргумента get_member(1):

```xml
<?xml version='1.0' encoding='utf-8'?>
<list><int>1</int></list>
```

Строка "ok" представляется как `<str>b2s=</str>`: b2s= — base64 от UTF-8.
Это не шифрование. Такая форма сохраняет NUL, CR, символы `<`, `&` и прочие
значения, с которыми прямое XML-представление может дать ошибку или
нормализацию. Для редких одиночных суррогатов Python выбран surrogatepass,
симметричный при кодировании и декодировании. Внешний клиент должен повторять
эту договорённость; для обычного Unicode используется стандартный UTF-8.

_element рекурсивно строит дерево; _value выполняет обратное преобразование.
Вложенность ограничена 32 уровнями. Неизвестные теги, лишние атрибуты,
дочерние узлы у скаляров и некорректный base64 отклоняются. defusedxml
запрещает DTD и внешние сущности. Тело всё равно остаётся XML, а не JSON.
JSON используется исключительно как удобный синтаксис команд локальной консоли.

## 8 Почему заголовки нельзя сделать одинаковыми

Оба заголовка имеют длину семь байт, но границы полей различаются.
Запрос содержит двухбайтовый код и четырёхбайтовую длину; ответ —
однобайтовый код и пятибайтовую длину. `reply` выбирает направление кадра.
`int.to_bytes(..., "big")` записывает число старшим байтом вперёд.

Для кода 10 и тела из трёх байт заголовки выглядят так:

```text
Запрос: 01 | 00 0A | 00 00 00 03
Ответ:  01 | 0A    | 00 00 00 00 03
```

Число три здесь — длина в байтах, не размер строки в символах. Кириллица
в UTF-8 занимает несколько байтов. Перед упаковкой длина вычисляется
после сериализации XML. Большая возможная длина в поле протокола не означает,
что приложение обязано выделять такую память: установлен лимит 1 MiB.

## 9 Почему нужен read_exact

TCP передаёт непрерывный поток, а не сообщения. sock.recv(7) вправе вернуть
1, 3 или 7 байт. Поэтому read_exact накапливает данные в bytearray, пока
не получит нужную длину. Пустой результат recv означает закрытие соединения;
если кадр ещё не дочитан, это ошибка, а не пустое успешное сообщение.

Сначала полностью читаются семь байт заголовка. Версия и размер проверяются
до получения тела. Затем read_exact читает ровно заявленный размер XML.
Фрагментация тестируется настоящей парой сокетов: отправитель передаёт
кадр по одному байту. Отдельно проверяется оборванное тело.

Одно соединение обслуживает один запрос. Это проще, чем поддержка нескольких
запросов, идентификаторов корреляции и переподключений внутри одного сеанса.
Клиент создаёт соединение на каждый вызов и закрывает его через with.

## 10 Что делает сервер при ошибке

Handler.handle получает кадр, пишет REQUEST в журнал, проверяет код и
декодирует аргументы. _dispatch допускает только десять операций из NAMES.
Произвольные имена атрибутов и исполнение кода исключены.

При create размер успешного ответа проверяется заранее, до вставки.
Иначе запись у лимита могла бы сохраниться, а клиент получил бы ошибку,
поскольку оболочка ответа немного длиннее оболочки запроса. Этот случай
зафиксирован регрессионным тестом test_large_create_error_does_not_insert.

При неизвестной операции сервер отвечает кодом 0: двухбайтовое неизвестное
значение запроса не обрезается до однобайтового ответа. Ошибка одного запроса
не останавливает сервер. REQUEST_ERROR, RESPONSE и SEND_ERROR также
направляются в stdout через logging, настроенный в __main__.py.

Если полная выборка превышает 1 MiB, сервер возвращает ошибку размера;
пагинация заданием не предусмотрена. Данные при чтении не меняются.
Потеря соединения после успешной вставки остаётся обычной неоднозначностью
сетевого вызова: exactly-once и идемпотентные повторы протокол не обещает.
Это локальный учебный прототип; аутентификация и TLS заданием не требуются.

## 11 Как работает REPL

REPL означает Read–Evaluate–Print Loop: прочитать, выполнить, вывести,
повторить. Здесь Evaluate означает вызов разрешённого метода, а не eval.

```json
{"method":"create_member","args":[[1,1000,"127.0.0.1","ru"]]}
{"method":"get_member","args":[1]}
{"method":"get_member","args":[999]}
```

В первом запросе внешний список args содержит единственный аргумент row,
который сам является списком. Во втором args содержит один целый uid.
Третий вызов показывает обработку отсутствующего ключа. Ошибка не выходит
за пределы execute_line: после сообщения можно вводить следующую команду.
Пустая строка пропускается, help показывает методы, quit завершает цикл.

## 12 Чем MBT отличается от обычного примера

Один успешный пример доказывает лишь работу одной последовательности.
RuleBasedStateMachine строит множество последовательностей: создание,
чтение, дубликаты, неправильные поля, отсутствующие связи и сдвиг времени.
Эталон хранит собственные словари и не использует алгоритм Store.

@initialize получает генерируемые строки и duration, создаёт цепочку связей,
два ответа с одинаковой проекцией и ответ на границе 540 секунд.
@rule задаёт действия; Hypothesis генерирует аргументы и порядок.
@invariant сравнивает состояния после каждого шага. Проекция эталона
вычисляется декартовым произведением трёх таблиц и условиями соединения:
это другой алгоритм, чем индексный поиск в основной модели.

Сервер для каждого примера новый, порт назначает ОС, а teardown освобождает
ресурсы. К клиенту обращаются через настоящие TCP-сокеты, поэтому одновременно
проверяются XML, заголовки, диспетчеризация, модель и обратный ответ.
Часы внедряются как функция clock; Hypothesis может сдвигать время без sleep.

Параметры 40 примеров и максимум 35 действий ограничивают длительность
проверки. Hypothesis может завершить отдельный сценарий раньше, поэтому
не следует выдавать их произведение за точное число выполненных действий.
При обнаружении сбоя библиотека пытается уменьшить сценарий до контрпримера.

## 13 Как читать покрытие

`coverage run --branch -m pytest tests/test_mbt.py -q` запускает только MBT.
В отчёт не подмешиваются обычные тесты. Stmts — исполняемые строки,
Miss — пропущенные строки, Branch — возможные переходы, BrPart — частично
покрытые ветвления. Coverage учитывает и строки, и переходы.

Скрипт check_mbt_coverage.py читает JSON coverage и проверяет тела всех десяти
методов Store и RpcClient. Дополнительно он требует отсутствие пропущенных
строк и ветвей model.py и schema.py. Процент всего проекта ниже: MBT клиента
не вызывает CLI и REPL, а часть защитных сетевых ветвей нужна только при
повреждённых кадрах. Полная таблица сохранена без исключения таких файлов.
